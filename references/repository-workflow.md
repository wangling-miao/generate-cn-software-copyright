# 仓库分析与材料撰写工作流

## 1. 先确认不可推断的法律信息

不得从仓库作者、Git 用户名、公司域名或包名推断著作权人。以下信息必须来自用户、正式登记资料或明确的项目文件：

- 软件全称、简称、版本号；
- 著作权人；
- 开发完成日期；
- 发表状态；
- 合作开发、委托开发、受让、继承或基于他人软件修改等权属情况。

缺少这些信息时，只能生成 draft，不能把材料称为“可提交终稿”。

## 2. 读取项目真实证据

优先检查：

- README、部署文档、架构文档和产品说明；
- `go.mod`、`package.json`、`pyproject.toml`、`pom.xml`、Docker Compose、Helm、环境样例；
- 前端路由、菜单、页面组件；
- 后端路由、控制器、服务、数据库模型和迁移；
- 认证、权限、日志、配置、导入导出和第三方接口实现；
- 已存在的截图、测试环境、演示账号和启动脚本。

不得只根据文件名编造功能。每个写入说明书的功能都应能定位到代码、页面、接口、文档或真实运行结果。

## 3. 选择可交存源码

默认规则：

- 只处理 Git 跟踪文件；非 Git 项目才扫描目录；
- 排除依赖、第三方代码、构建产物、自动生成代码、测试夹具、密钥和环境文件；
- 默认排除测试代码，优先交存核心生产代码；
- 通过 `priority_globs` 把入口、核心业务和关键算法排在前面；
- 合并后的源程序超过 3000 行时，提取前 1500 行和后 1500 行；不足 3000 行时提交全部；
- 保留 `audit/source-manifest.json` 和哈希，用于证明选择过程可复现。

若项目含多种语言，可以共同交存，但应优先保证内容属于同一软件版本且能体现核心功能。

## 4. 获取真实截图

- 优先启动软件并通过真实操作截取界面；Web 项目可使用仓库已有 Playwright/Cypress 流程或 Agent 可用的浏览器工具。
- 截图应与说明文字一一对应，包含足够的界面上下文，但不要暴露真实个人信息、令牌、密钥或敏感业务数据。
- 不得用设计稿、空白页面、AI 生成界面或无关图片冒充运行截图。
- 命令行、API 或库软件可使用终端运行结果、接口调试界面或示例程序运行界面，但必须真实执行。

## 5. 撰写说明书

使用事实性语言说明：用途、输入、处理、输出、操作路径、权限和异常处理。避免：

- 与代码不符的营销性描述；
- “智能”“先进”“领先”等没有证据的结论；
- 只列功能名称而不写用户如何操作和系统如何处理；
- 把计划功能、未接通页面或测试桩写成已实现能力。

## 6. 构建和强制校验

运行：

```bash
python scripts/build_materials.py \
  --project /path/to/repository \
  --config /path/to/software-copyright.json \
  --mode final \
  --compile \
  --validate
```

必须查看：

- `audit/validation-report.md`；
- `audit/source-manifest.json`；
- 两份 PDF 的每一页；
- LaTeX 编译日志中的缺图、字体、溢出和错误。

只要存在 error，就不能声称材料已经完成。warning 必须逐项判断并在交付说明中披露。
